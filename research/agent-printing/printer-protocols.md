# Printer, camera and CFS protocol capabilities

Research snapshot: 2026-10-01. Scope is the confirmed fleet class (one K1 Max, three K1 SE, two Creality Hi), without assuming per-unit attachments, firmware, account binding, or network configuration. No device/network/cloud connections were made.

## Decision-useful conclusion

The current AI send path does **not** simply use the legacy `DeviceManager`/`NetworkAgent` print-job route. `MCPChatPanel::ExecuteAISendToPrinterAction` opens `AISendWorkflowService`; that service sends via `EasyPrintSender` and `RemotePrinterManager`. The LAN uploader includes an open Moonraker-style HTTP upload implementation selected by printer type/metadata, while print start and generic pause/resume/stop are forwarded into the embedded device-manager webview JavaScript interface. The legacy `DeviceManager` route still documents Creality Print's local/cloud MQTT integration, but should be treated as an alternative/older path unless a specific current workflow is shown to call it.

The code therefore gives a useful local implementation reference, including a direct Moonraker upload branch, but does not establish that an external service can reuse Creality Print's private webview bridge or that stock Creality printers expose a supported stable public API. Keep adapters replaceable and qualify each actual machine.

Moonraker offers a documented local HTTP/WebSocket interface with upload, start, pause/resume/cancel, status subscriptions and configured webcam metadata. It is a clean adapter boundary only if a given machine is confirmed to expose Moonraker; the sources reviewed do not establish that stock firmware on these three model families does so. Rooted/modified firmware is a separate, unsupported per-unit option with firmware/update and support implications. Do not treat rooted Klipper access as the fleet baseline.

**Acknowledgement semantics:** Treat every control call as a request, not proof of resulting state. Moonraker's documented control response is `"ok"`; verify pause through subsequent `print_stats.state == "paused"` (and subscribe/query for terminal job state). The current bridge's `DoPrintControl` returns `accepted: true` after `request_print_control` forwards to the webview; that proves dispatch only. The webview bundle contains `sendPrintControl` handlers calling its device interface, but the C++ source does not expose the ultimate device acknowledgement. The legacy MQTT path also separates command publication from later `RUNNING`/`PAUSE` observations. For automatic failure response, send pause once with an idempotent job/action key at the service layer, then wait for fresh paused status; if not observed by a bounded deadline, alert and hold further action. Resume requires explicit owner authorization, then verify fresh running state.

## Model-family evidence and limits

- **K1 Max:** CrealityOS release notes identify camera fixes for K1 Max, supporting that the model family has camera functionality; the K1 Series CFS Upgrade Accessory Kit manual explicitly lists a K1 Max-specific kit. These facts do not prove the owner's six units have a functioning camera/CFS installed or current firmware. [CrealityOS changelog](https://wiki.creality.com/en/k1-flagship-series/k1-max/CrealityOS_ChangeList_1_3_2_20), [K1 CFS kit manual](https://wiki.creality.com/products/k1-series-cfs-upgrade-accessory-kit/%E5%A4%9A%E8%AF%AD%E7%A7%8D%E8%AF%B4%E6%98%8E%E4%B9%A6/k1_series_cfs_upgrade_accessory_kit-sm-001_user_manual%28en%29.pdf)
- **K1 SE:** Its official manual lists LAN and Creality Cloud printing. The K1 CFS kit manual lists K1 SE and specifies a different kit configuration from K1 Max, so CFS is an upgrade/accessory path, not a safe assumption about installed hardware. The reviewed K1 SE specs excerpt does not list a camera; camera presence must be recorded per unit. [K1 SE manual](https://wiki.creality.com/products/fully-enclosed/k1se/%E5%A4%9A%E8%AF%AD%E7%A7%8D%E8%AF%B4%E6%98%8E%E4%B9%A6/k1_se-sm-001_user_manual%28en%29.pdf), [K1 CFS kit manual](https://wiki.creality.com/products/k1-series-cfs-upgrade-accessory-kit/%E5%A4%9A%E8%AF%AD%E7%A7%8D%E8%AF%B4%E6%98%8E%E4%B9%A6/k1_series_cfs_upgrade_accessory_kit-sm-001_user_manual%28en%29.pdf)
- **Creality Hi:** Official support material documents the Creality Hi-to-CFS physical connection (including a 485 communication cable and PTFE path), establishing that CFS compatibility exists but is optional hardware. It does not establish any particular unit's installed CFS or camera. Creality's CFS troubleshooting also shows feed paths and filament sensor failures can require physical intervention, so a successful load command is not proof filament reached the extruder. [Hi buffer-holder/CFS installation](https://wiki.creality.com/en/cr-series/creality-hi/install-filament-buffer-holder), [Hi extruder maintenance](https://wiki.creality.com/en/cr-series/creality-hi/extruder-kit)

Across all models, Creality Print's own UI warns that CFS slot assignment can require firmware updates, mapping may be sequential-only, and unknown filament mappings need human confirmation. It blocks or warns about TPU and carbon/glass-filled filaments in CFS. Thus external spool and CFS should be modeled as different feed sources, with a verified live slot/material/color record and explicit incompatibility checks. ## Primary protocol sources

- Moonraker describes itself as a web server exposing APIs to Klipper; the external API separates HTTP file transfer from WebSocket status events. [Introduction](https://moonraker.readthedocs.io/en/latest/external_api/introduction/)
- Moonraker documents file upload with optional SHA-256 checksum and optional `print=true`. [File Management](https://moonraker.readthedocs.io/en/latest/external_api/file_manager/)
- Moonraker documents print start/pause/resume/cancel endpoints and printer-state requirements. [Printer Administration](https://moonraker.readthedocs.io/en/latest/external_api/printer/)
- Moonraker webcam management configures named camera stream URLs and settings; it does not make a camera exist. [Webcam configuration](https://moonraker.readthedocs.io/en/stable/configuration/#webcam)
- Creality official manuals/changelogs cited above establish connectivity choices and accessory/model facts only. I found no Creality-published API contract covering discovery, camera frames, MQTT control or CFS slot/load/unload for this combined fleet.

## Recommendation and qualification gates

1. Put printer I/O behind a local adapter interface. The current AI route offers implementation patterns: per-type upload dispatch, an HTTP Moonraker uploader, and a bridge-mediated print command/control action. The bridge is coupled to running Creality Print and is not shown here as a callable external API. A direct Moonraker adapter is preferable for units proven to expose it; keep the Creality LAN/cloud route as an adapter only after qualifying its private protocol or a supported app boundary.
2. Do not hardcode LAN MQTT topics, guessed ports, FTP behavior or camera URLs based on source reverse-engineering. Establish one approved, read-only, per-unit qualification session later: identify model/firmware and LAN/cloud mode; confirm live status freshness; confirm camera stream and timestamp; inventory CFS and slot/material/color; then separately test upload and job controls under human observation.
3. Printer model family is not enough to select jobs. Maintain per-unit capabilities with evidence timestamps (LAN path, camera present/healthy, CFS attached, supported mapping mode, firmware, spool source and material-known status). A stale/missing camera must hold the job per the owner's requirement.
4. Failure monitoring cannot rely on progress alone. Expose printer-reported errors/status plus camera frames if available. Owner policy is to automatically pause when a failure is validated and ask before resuming. Implement this as an observed-state transition: a command accepted by the network is not a confirmed pause. Camera AI monitoring is a separate locally run perception system and needs model-specific validation; neither Creality Print's camera URL helper nor Moonraker webcam metadata proves spaghetti/failure recognition or bed-clearance accuracy.
5. Do not use a camera empty-bed reference as sole readiness proof unless a fresh live frame is obtained and local recognition confidence has been qualified per camera/view. The current research establishes no image API, camera attachment inventory, or safety accuracy.

## Explicit unknowns

Actual firmware/root state, LAN-mode and account bindings, camera/CFS attachments on each of six units, supported stock local upload/start/control parity, endpoint credentials/security, stream freshness, CFS slot state and allowed command vocabulary, and whether the printer families expose Moonraker remain live qualification items. No operational reachability or install-state claim is made.
