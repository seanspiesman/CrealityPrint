# Background integration paths for Creality Print on macOS

## Finding

There is no single existing interface that satisfies “background Mac service, automatic preparation and start, and inspectable Creality project.” The best reuse split is (a) a model-agnostic local job/service layer with a standard MCP/API front end, (b) a subprocess adapter to Creality Print CLI for deterministic headless slicing where its semantics fit, and (c) an explicitly versioned IPC adapter into the running Creality Print GUI for scene editing, native project save, and its existing send workflow. A cleanly installed MCP server cannot call `SlicerBridge` directly: that singleton executes actions in the running wx GUI, and the current inbound agent transports are app-owned WebSocket/MQTT connections, not an exposed local MCP endpoint. If the GUI is unavailable, CLI-only operations are narrower and cannot substitute for the GUI send workflow.

This recommendation is a source-based architectural inference, not a proven macOS deployment design. No binary, printer, cloud account, or local service was exercised.

## Completion, project and preparation details

- **CLI completion:** source writes G-code as `plate_N.gcode` when `need_gcode_file` is set, otherwise uses/removes a temporary G-code path; on successful plate slicing it marks the result valid and records per-plate timing/count/warnings. [`SliceCommand.cpp`](../../src/slic3r/CLI/SliceCommand.cpp#L1244), [success/result](../../src/slic3r/CLI/SliceCommand.cpp#L1282). CLI errors are returned through codes and, on Linux builds only, `result.json` ([writer](../../src/slic3r/CLI/SliceCommand.cpp#L556)). The macOS completion contract should be based on child exit status plus a verified output manifest/artifact hashes, not a guessed Linux sidecar.
- **GUI completion/staleness:** bridge’s immediate result means request accepted/started; a later panel loop requires the background slice to have been observed and `current_plate.slice_result_valid`, then it emits the completion or starts G-code export. [`MCPChatPanel.cpp`](../../src/slic3r/GUI/simple/MCPChatPanel.cpp#L785). The state result refers to current plate, so serialize jobs and capture a scene/settings fingerprint at start; reject completion if project generation, target plate, or configuration no longer matches. Fingerprinting is a recommendation/inference; no request-scoped fingerprint is shown in the cited path.
- **Inspectability:** normal project save is a `.3mf`/`.cxprj` export, and normal save includes G-code unless caller sets `with_gcode=false`. [`Plater.cpp`](../../src/slic3r/GUI/Plater.cpp#L17023). The CLI slices 3MF in memory; the documented output directory is for G-code/result files. The inspected path does not establish that slicing rewrites the original editable project or exports all GUI scene transformations as an inspectable `.3mf`. Keep the downloaded source and prepared project as explicit job artifacts; do not treat `.gcode.3mf` as a saved editable project without verifying its contents.
- **Settings applicability:** GUI slice accepts printer/process/material profile names and current project settings; CLI config priority is command-line overrides over embedded 3MF settings, but its explicit external preset loading is rejected for 3MF. [`SlicerBridgeActionRegistry.cpp`](../../src/slic3r/GUI/simple/bridge/SlicerBridgeActionRegistry.cpp#L327), [`CLI.cpp`](../../src/slic3r/CLI/CLI.cpp#L170), [`SliceCommand.cpp`](../../src/slic3r/CLI/SliceCommand.cpp#L1996). Therefore prepare a 3MF by applying its settings before CLI slicing or choose STL/OBJ plus compatible machine/process/material JSON; do not assume supplying JSON replaces embedded 3MF configuration.
- **Transforms/repair/orientation:** CLI includes automatic bed arrangement, including rotation/bed placement, in its slice pipeline ([`SliceCommand.cpp`](../../src/slic3r/CLI/SliceCommand.cpp#L2174), result applied at [L2223](../../src/slic3r/CLI/SliceCommand.cpp#L2223)). GUI bridge offers explicit repair and auto-orient tools ([registry](../../src/slic3r/GUI/simple/bridge/SlicerBridgeActionRegistry.cpp#L258)). No CLI-level repair or auto-orient option was found in the command definitions searched. The arrangement mutates CLI’s in-memory model; source inspected here does not show that this result is persisted to a `.3mf`.
- **Cancel:** GUI send workflow exposes cancel/retry controls through its UI handlers, but the inspected bridge has no matching stable `cancel_slice` API. CLI invocation can be stopped by its parent process at the OS level; a supported graceful cancel/partial-output cleanup contract was not found. A service should own cancellation, ensure process termination, clean partial files, and mark the job canceled only after child exit is observed.

## MCP/API and authorization boundary

`SlicerBridge::GetAvailableToolsJSON()` serializes action names, JSON input schema and `requires_confirm` metadata ([`SlicerBridge.cpp`](../../src/slic3r/GUI/simple/bridge/SlicerBridge.cpp#L158)). This is a tool catalogue, not a network MCP server. The dispatcher directly looks up and invokes the action executor; its implementation does not itself enforce `requires_confirm` ([`SlicerBridge.cpp`](../../src/slic3r/GUI/simple/bridge/SlicerBridge.cpp#L336)). The current CxAgent path is a WebSocket client and the SAgent path is MQTT in `MCPChatPanel`; those are upstream-facing app connections, not an external local endpoint ([`CxAgentClientBridge.cpp`](../../src/slic3r/GUI/simple/bridge/CxAgentClientBridge.cpp#L107), [`SAgentMqttBridge.hpp`](../../src/slic3r/GUI/simple/bridge/SAgentMqttBridge.hpp#L19)). Consequently, “MCP” in current names/metadata must not be interpreted as MCP stdio or Streamable HTTP support.

The MCP specification revision consulted, [2025-11-25 Transports](https://modelcontextprotocol.io/specification/2025-11-25/basic/transports), defines stdio and Streamable HTTP; stdio launches a child process, while local HTTP servers should bind to loopback, validate `Origin`, and use authentication. The [2025-11-25 Authorization spec](https://modelcontextprotocol.io/specification/2025-11-25/basic/authorization) defines HTTP transport authorization, while stdio should get credentials from the environment. For this Mac, a persistent LaunchAgent-style service could expose Streamable HTTP on loopback and/or have MCP clients launch a stdio shim; the same internal job engine should serve both. Avoid listening on all interfaces. Enforce authorization/action policy in the service/bridge, not only an agent prompt or `requires_confirm` field.

One implementation risk exposed by source: `SlicerBridge::Execute` logs the complete JSON argument payload ([`SlicerBridge.cpp`](../../src/slic3r/GUI/simple/bridge/SlicerBridge.cpp#L336)). New tool schemas should not carry cloud credentials or camera image bytes in ordinary arguments, and logging needs redaction/size bounds before external use.

## Suggested interface shape for the spec

Define a persistent local job service around operations such as `inspect_printers`, `download_model`, `prepare_project`, `validate_project`, `slice_project`, `start_job`, `get_job`, `cancel_job`, and `get_artifact`. Each mutation receives an idempotency key and produces a durable job ID; every result records input hash, source/license attribution, app/CLI version, printer profile, material mapping, settings diff, prepared `.3mf` path/hash, G-code path/hash, validation warnings, and terminal state. The service owns queueing and process lifecycle; the Qwen/other model consumes only the stable agent tools/API contract.

Keep `prepare_project` explicitly GUI-dependent until CLI transforms and project export have a proven path. The app adapter should execute GUI operations on its UI thread, return progress/terminal completion through IPC, export a new versioned `.3mf` to a job workspace, and refuse stale result association. Use CLI as a headless worker only for project/preset combinations documented above. A dedicated printer adapter is required for `start_job` and telemetry if this workflow must keep operating when the GUI is closed; that adapter is intentionally unresolved here.

### Remaining evidence gaps

1. Whether the released macOS binary accepts `--slice` without presenting/depending on interactive GUI state, exact supported flags, sidecars and exit semantics.
2. Whether CLI can programmatically export a fully editable prepared `.3mf` after arrangement/settings changes, and which data/plate structures survive that export.
3. Whether the selected K1 Max/K1 SE/Creality Hi models can use the existing GUI send delegate, and whether it works if the app is minimized, backgrounded, or disconnected.
4. External service/app IPC lifecycle, macOS LaunchAgent login/sleep behavior, crash recovery and duplicate-start/idempotency design.
5. Exact policy and enforcement for unattended start. Current action metadata includes a `requires_confirm` field, while bridge dispatch itself invokes the action directly; downstream UI/backend enforcement was not fully audited.
6. Per-job freshness binding, overlap/serialization and cancellation of active GUI/CLI slices, with no stale G-code accidentally sent.
7. Current third-party MCP client compatibility and authentication choice. Protocol docs state the transport rules; no client was configured or tested.

## Validation boundary

Read-only source inspection plus the primary MCP specification pages linked above. No build, CLI execution, GUI operation, local service, model download, printer connection, live image capture, printer send, or physical print was performed. Source behavior may differ in the installed macOS release `7.2.2.5483`; the checkout was not compared to its shipped symbols/source revision in this task.
