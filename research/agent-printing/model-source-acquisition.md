# Model-source acquisition interfaces and limits

**Research date:** 2026-10-01. This is a primary-source survey of public discovery and acquisition interfaces for Printables, Thingiverse, MakerWorld, direct URLs, and owner-supplied local files. It did not log into an account, download a model, invoke a hidden endpoint, or test authenticated/automated access. Site and API behavior can change.

**Owner-set first-release priority set:** Printables, Thingiverse, and MakerWorld, with no ranking among them. This is a product priority, not evidence that any of them supports qualified unattended acquisition. The owner has also said there should be no account-backed source integrations in the first release; when an item cannot be obtained through a qualified public path, use an owner-supplied file.

## Recommended acquisition contract (inference)

Build one local **source adapter** interface that returns candidate metadata for review: canonical source URL and platform ID where available; title/creator; visible license text or “not displayed”; candidate required parts/variants and file names; format and published version where visible; and retrieval time. Hashes, actual file sizes, and archive manifests belong to the acquired-artifact record and can only be populated after acquisition. Separate `search candidates`, `inspect selected candidate`, and `acquire selected files`; automatically acquire all required parts/variants when unambiguous, and ask when required parts or variant choice is ambiguous. If official API terms/auth are not established for a source, do not reverse-engineer hidden calls.

Implement local-file import as the fallback first. The three named sites remain an unranked owner-selected source set; qualify each public acquisition path independently before unattended use. Do not include account-backed integrations in release one. This is an engineering recommendation based on the documentation gaps, not a claim that the sites prohibit other integrations. Once geometry is acquired, prepare against the selected verified local Creality printer/process/material profiles and re-slice. The owner has authorized model authoring without another approval; for assembly-required hardware, ask when necessary hardware is missing or unknown.

## File and license handling

- Treat downloaded archives, meshes, project files and metadata as untrusted. Reject path traversal and excessive expanded size; record what was extracted. Preserve the unmodified source separately from any normalized, repaired or sliced derivative.
- Keep model geometry/project input distinct from supplied G-code. Printables explicitly exposes G-code as a separate file class. For this workflow, supplied G-code should be metadata-only evidence and should not be dispatched: import the model/project, inspect embedded settings and re-slice using the selected verified Creality printer/process/material profiles. Creality’s importer may include embedded profile information and its 3MF may include `plate_N.gcode`; see [reliable-preparation.md](https://github.com/seanspiesman/CrealityPrint/blob/01b68f16/research/agent-printing/reliable-preparation.md).
- Store the site’s license label and URL with the exact downloaded version and file. The Printables terms make the selected creator license relevant and MakerWorld pages can carry Standard Digital File License or creator/subscriber terms. This report makes no legal interpretation and does not infer permission from “free download.”
- Candidate review should show preview, source, creator, published license, exact file/variant and profile provenance before acquisition when an agent is finding models. An owner-selected local file can proceed through preparation without a source-site access step.

## Unknowns to resolve before implementation

1. Whether anonymous public acquisition can be qualified for each site without account-backed integration; owner-supplied files are the fallback.
2. Thingiverse’s current API schemas/auth/rate limits and permitted unattended use; the Swagger view was not inspectable here.
3. Whether MakerWorld has a first-party public API/automation contract. None was established here; this is not proof no private or partner API exists.
4. What metadata may be fetched automatically from public listing pages, and what access/volume limits apply.
5. Maximum download/archive/expanded sizes; allowed URL schemes/domains; file extensions/formats; how subscription/payment gates are handled; and what makes a required parts/variant set ambiguous enough to ask.
6. Keep creator/license labels and attribution as descriptive source metadata; exact terms for the acquired item remain visible to the owner, without this service inferring unstated rights.

**Evidence limit:** official search/model pages and terms were read, but no account entitlement, direct download, API credential, rate limit, automation permission, or live access was verified. Exact interface support must be confirmed against current official developer docs and a later authorized qualification test before building unattended adapters.
